# Windows-local Whisper and NVIDIA Parakeet runtimes

Research findings for [GitHub issue #9](https://github.com/m-lahme/local-dictation/issues/9), captured on 2026-07-17. This document answers the runtime question; it does **not** choose the V1 model catalog, hardware recommendation thresholds, or model lifecycle. Those are owner decisions in issue #10.

## Executive conclusion (reasoned, not yet a product decision)

The smallest credible native-Windows shortlist is:

1. **Whisper:** `whisper.cpp` as the native integration candidate, with `faster-whisper`/CTranslate2 retained as a performance challenger.
2. **Parakeet:** `sherpa-onnx` as the native integration candidate, benchmarking both the 126 MiB English Parakeet TDT-CTC 110M INT8 conversion and the 640 MiB, 25-language Parakeet TDT 0.6B v3 INT8 conversion. Keep `onnx-asr` as a Python challenger where DirectML/TensorRT/provider breadth could outweigh native integration cost.
3. **Reference baselines:** NVIDIA NeMo or Hugging Face Transformers for Parakeet fidelity, and the OpenAI reference implementation for Whisper fidelity. They should not be assumed to be V1 deployment runtimes before packaging and cancellation tests.

This shortlist is not a V1 catalog selection. The benchmark below and the owner choices listed at the end are still required.

### Concrete benchmark and prototype plan

Freeze every runtime/version, model digest, compiler flags, execution provider, thread count, and precision. Run the same harness on clean Windows 11 machines with power mode fixed and after one warm-up pass.

#### Hardware cells

1. CPU-only x64: one lower-power laptop and one contemporary desktop, recording ISA, physical/logical cores, memory bandwidth proxy, and available RAM.
2. NVIDIA: at least one 6–8 GB GPU and one 12+ GB GPU; test CUDA versions actually eligible for the frozen runtime.
3. Cross-vendor GPU: one Intel or AMD Windows 11 system for `whisper.cpp` Vulkan only. Do not infer Parakeet GPU support from this cell.

#### Audio set

- A consented, locally retained owner-dictation set split into short (2–10 s), normal (10–60 s), and long (1–5 min) Dictations.
- Quiet, keyboard/fan noise, far-field microphone, Bluetooth, and accented speech strata.
- A fixed recognition-term challenge list containing names, compounds, abbreviations, and ambiguous phrases; run each clip with no terms and with identical Recognition terms.
- Languages remain parameterized. At minimum, test every language the owner proposes to expose; do not infer the V1 language catalog from the models' theoretical lists.
- Include silence, clipped start/end, code switching, and 100 ms/1 s/10 s/60 s cancellation fixtures.

#### Measurements and acceptance inputs

| Area | Measurement |
| --- | --- |
| Accuracy | Normalized WER/CER, punctuation/case score, hallucination rate on silence, and recognition-term recall/false-accept delta. Keep deterministic Replacement rules out of this comparison. |
| Responsiveness | Cold model-load time, warm end-of-capture-to-final-text p50/p95/p99, real-time factor, and first partial time where simulated streaming is tested. |
| Resources | Peak/private working set, committed RAM, peak VRAM, steady-state loaded footprint, CPU time, GPU utilization, and energy proxy. |
| Packaging | Compressed runtime closure, installed runtime closure, model download bytes, expanded model bytes, number of files, first-run download time, and signature/license-notice inventory. |
| Metadata | Language ID accuracy/confidence availability; segment/word/token timestamp coverage and absolute boundary error against a hand-aligned subset. |
| Cancellation | Time from cancel signal to inference stop and return to idle at each fixture length; whether CPU/GPU activity stops; whether audio/partial text survives; model usability after 100 repeated cancels. Target threshold is an owner decision. |
| Reliability | 1000 sequential Dictations, repeated load/unload, device/provider fallback, corrupt/partial model download, insufficient RAM/VRAM, and worker crash/restart. |

Run paired comparisons with identical audio and decoding settings where semantics align. Report confidence intervals, not only averages. Preserve raw JSON/CSV results and a manifest containing file hashes so later model/runtime releases can be compared reproducibly.

The cancellation prototype has two paths:

- `whisper.cpp`: set an atomic cancellation flag consumed by `abort_callback`; verify bounded exit from both encoder and decoder and safe reuse of the context.
- faster-whisper, sherpa-onnx, onnx-asr, and NeMo/Transformers: invoke inference in a dedicated worker process; first test any cooperative boundary available, then terminate the worker after a bounded grace interval. Measure restart/load penalty and confirm that cancellation creates no History entry, matching the product contract.

## Reasoned recommendations

1. **Prototype `whisper.cpp` and `sherpa-onnx` first.** They expose native interfaces, publish Windows artifacts, cover the two required engine families, and avoid making Python part of the Management process.
2. **Keep faster-whisper and onnx-asr as challengers, not foregone dependencies.** They widen throughput and provider coverage, but Python packaging and the lack of documented hard-cancel paths are material integration costs.
3. **Use NVIDIA's implementation as the Parakeet oracle.** Compare identical audio against the sherpa ONNX conversion before accepting the conversion, especially for languages, punctuation/case, timestamps, and phrase biasing.
4. **Design Recognition terms as capability-negotiated hints.** Whisper prompt context, sherpa hotwords, and NeMo phrase boosting have different semantics. The UI/domain contract already says hints are not guarantees; the backend interface should report support and limits rather than pretending equivalence.
5. **Plan process isolation at the transcription boundary unless the architecture ticket proves otherwise.** `whisper.cpp` has cooperative abort, but sherpa and Python runtimes do not establish bounded cancellation. A killable worker is the only cross-runtime guarantee identified here. This is an architectural input, not a final process decision.
6. **Separate runtime delivery from model delivery.** The range from 126 MiB to multi-gigabyte models and the 678 MB CUDA-enabled `whisper.cpp` archive makes a single all-model installer wasteful. Exact download/catalog policy remains issue #10's decision.

## Rejected alternatives for the V1 shortlist

- **OpenAI's PyTorch Whisper implementation as the deployment runtime:** authoritative for fidelity but intended as a Python reference, with a large PyTorch dependency and no native bounded-cancel contract. Keep it only as a benchmark oracle.
- **NVIDIA NeMo or Riva as the default native Windows runtime:** NeMo's official installation path is Linux-oriented and dependency-heavy; it is valuable as the model oracle, not a small Windows embedding. Riva is a server/container deployment surface rather than an in-process native Windows runtime.
- **A product-owned raw ONNX Runtime decoder:** technically possible, but it would take ownership of feature extraction, tokenization, TDT/CTC decoding, timestamps, contextual biasing, and model-conversion compatibility already handled by sherpa-onnx or onnx-asr. Revisit only if both prototypes fail acceptance gates.
- **DirectML as a promised Parakeet provider:** current sherpa public provider documentation names CPU/CUDA/CoreML, not DirectML. Do not turn an unverified build path into a product claim.
- **Community repackagings or model conversions:** excluded from evidence and shortlist because the ticket requires primary sources and a supportable provenance chain.

## Remaining risks

- Sherpa's Parakeet artifacts are third-party conversions of NVIDIA models; release cadence, exact numerical fidelity, metadata preservation, and conversion reproducibility must be tested and pinned.
- CC BY 4.0 requires attribution for Parakeet model distribution. The installer, model manager, About/licenses view, and offline notices need a verified attribution design.
- Parakeet Unified uses the NVIDIA Open Model License instead of CC BY 4.0; eligibility and notice obligations must be reviewed separately before it enters any catalog.
- Recognition-term effectiveness is data- and decoder-dependent. Whisper prompts can be ignored; sherpa hotwords require modified beam search and a tuned score; the 110M CTC export does not share that path.
- Package sizes above mix authoritative compressed release assets and expanded model contents. Final installer/download numbers require a frozen dependency closure and must include VC++ runtime, ONNX Runtime/CUDA libraries, Python/PyTorch where applicable, and licenses.
- Model-reported language and timestamps are not automatically History-quality metadata. Store detected language only after the selected runtime/model passes reliability thresholds, as required by the domain baseline.
- Simulated streaming can increase repeated work and does not change V1's final-text-after-capture interaction. It should not be used to justify latency claims without measurement.

## Unresolved owner product decisions (issue #10 boundary)

Do not resolve these from this research alone:

1. Which languages V1 exposes and whether an English-only compact Parakeet option belongs in the catalog.
2. The V1 Whisper and Parakeet model variants, quantizations, and hardware recommendation rules.
3. Accuracy, warm latency, cancellation latency, RAM/VRAM, download-size, and disk-size acceptance thresholds.
4. Whether Recognition terms must be available for every selectable backend or may be shown as unsupported per model.
5. Whether CC BY 4.0 attribution and a third-party ONNX conversion are acceptable for packaged model downloads.
6. Whether models are downloaded on demand, offered during first-run setup, bundled, removable independently, and retained across app updates.
7. Whether transcription runs in-process or in a separate worker, subject to the architecture ticket and cancellation prototype.
